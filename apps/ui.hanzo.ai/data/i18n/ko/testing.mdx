모든 컴포넌트는 자기 이름으로 `data-slot` 을 찍습니다. 테스트는 버전이 바꿀 수 있는 마크업에 기대지 않고 컨트롤을 찾을 수 있습니다. 앱과 같이 `Hanzo` 아래에 마운트하세요. 루트는 모든 토큰이 비추는 설정을 지니고, 루트 테마가 없는 컴포넌트는 예외를 던집니다.

## 단위 테스트

```bash
pnpm add -D vitest jsdom @testing-library/react @testing-library/user-event
```

```ts title="vitest.config.ts"
import { defineConfig } from 'vitest/config'

export default defineConfig({
  resolve: {
    alias: {
      'react-native': 'react-native-web',
      '@react-native/assets-registry/registry': 'react-native-web/dist/modules/AssetRegistry',
    },
  },
  test: {
    environment: 'jsdom',
    server: { deps: { inline: [/@hanzogui\//, /@hanzo\/gui/, /react-native/] } },
  },
})
```

별칭은 번들러가 지닌 것과 같습니다. `inline` 목록이 중요합니다. 엔진 패키지는 ESM 을 다시 내보내는 CommonJS 로 나가고, external 로 두면 테마를 가진 모듈의 두 번째 사본으로 풀립니다. 프로바이더는 한 컨텍스트에 쓰고, 테마가 붙은 컴포넌트는 다른 것을 읽어 `Missing theme` 을 던집니다.

```tsx title="deploy.test.tsx"
import { Hanzo } from '@hanzo/ui'
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { expect, it, vi } from 'vitest'

import { Deploy } from './deploy'

const mount = (node: React.ReactNode) => render(<Hanzo>{node}</Hanzo>)

it('deploys on press', async () => {
  const onDeploy = vi.fn()
  mount(<Deploy onDeploy={onDeploy} />)
  await userEvent.click(screen.getByRole('button', { name: 'Deploy' }))
  expect(onDeploy).toHaveBeenCalledOnce()
})

it('renders the control', () => {
  const { container } = mount(<Deploy onDeploy={() => {}} />)
  expect(container.querySelector('[data-slot="button"]')).not.toBeNull()
})
```

## 캐스케이드 없는 DOM 안의 색

jsdom 은 `var()` 를 풀지 않고, 테스트에 그 문자열을 그대로 넘깁니다. 테마 단은 일부러 `var(--border, rgb(255 255 255 / .10))` 로 적혀 있습니다. 디자인 시트가 마운트되어 있으면 살아있는 캐스케이드를 따르고, 없으면 감사된 리터럴을 남기기 위해서입니다. jsdom 에서 테두리 대비를 주장하면 색과 함수 호출을 비교하게 됩니다. `substitute` 는 jsdom 이 밟지 않는 그 한 걸음을 밟습니다.

```ts
import { substitute } from '@hanzo/ui/css'

const border = substitute(getComputedStyle(el).borderColor)
// 'rgb(255 255 255 / .10)'
```

`vars` 맵이 없으면 이것은 근사가 아니라 정확합니다. jsdom 은 디자인 시트를 마운트하지 않으므로 `--border` 를 선언하는 것이 없고, 폴백은 같은 조건에서 브라우저가 계산할 것입니다. 자기 토큰을 선언하는 호스트를 본뜨려면 맵을 넘기세요. 이 모듈은 아무것도 임포트하지 않고 두 형식을 모두 내보내므로, 어느 러너에서든 불러올 수 있습니다.

## 브라우저가 계산한 것

빌드도, 타입 검사도, 단위 테스트도, 페이지에 한 번도 닿지 않은 스타일시트 위에서 통과합니다. 증명은 브라우저입니다. 앱을 빌드해 서빙하고, 마크업의 주장이 아니라 계산된 스타일을 주장합니다.

```ts title="e2e/app.spec.ts"
import { expect, test } from '@playwright/test'

test('the button is styled', async ({ page }) => {
  const errors: string[] = []
  page.on('pageerror', (e) => errors.push(e.message))
  await page.goto('/')
  const button = page.locator('[data-slot="button"]').first()
  await expect(button).toBeVisible()
  const bg = await button.evaluate((el) => getComputedStyle(el).backgroundColor)
  expect(bg).not.toBe('rgba(0, 0, 0, 0)')
  expect(errors).toEqual([])
})
```

패키지가 자신을 시험하는 방법이 이것입니다. 갤러리는 모든 배리언트의 모든 컴포넌트를 담은 하나의 목록입니다. 스타일시트 생성기가 그 목록을 렌더하고, 단위 테스트는 진짜 프로바이더 아래에서 그것을 렌더해 모든 슬롯 표식이 도착했는지 확인합니다. 쓰는 쪽의 테스트는 tarball 을 싸고, 저장소 밖의 앱에 설치합니다. 워크스페이스 링크는 쓰지 않습니다. 그것은 소스 트리를 통해 풀리고, tarball 에서 빠진 파일을 감추기 때문입니다. 빌드한 뒤 두 테마에서 390 과 1280 의 계산된 스타일과 스크린샷을 주장합니다. 워크스페이스 링크였다면, 그 테스트가 잡기 위해 있는 결함을 모두 내보냈을 것입니다.
